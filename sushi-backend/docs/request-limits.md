# Ограничения чувствительных запросов

Лимиты задаются в `src/rate-limit/rate-limit.policies.ts`. Учитываются все
попытки обращения к защищённому маршруту, включая неверные данные и повторы
с ключом идемпотентности. Лимиты разных маршрутов независимы.

| Действие                       | Идентификатор                       | Лимиты                     |
| ------------------------------ | ----------------------------------- | -------------------------- |
| Гостевой заказ                 | IP                                  | 10 за 10 минут и 30 за час |
| Заказ с авторизацией           | ID пользователя из проверенного JWT | 10 за 10 минут и 30 за час |
| Создание Telegram-сессии       | IP                                  | 5 за минуту и 20 за час    |
| Проверка Telegram-кода         | IP                                  | 20 за минуту               |
| Вход через Google              | IP                                  | 20 за минуту               |
| Команда `/start` Telegram-бота | Telegram ID отправителя             | 5 за минуту и 20 за час    |

При превышении HTTP API возвращает `429`, код `RATE_LIMITED`, число секунд
в `retryAfter` и заголовок `Retry-After`. Корзина и ключ попытки оформления
сохраняются. Клиент не повторяет запрос автоматически. Бот игнорирует команды
сверх лимита, чтобы не создавать поток ответов на спам.

## Общие счётчики

Счётчики находятся в PostgreSQL в таблице `RequestRateLimit`. Атомарный
`INSERT ... ON CONFLICT ... DO UPDATE` и время PostgreSQL обеспечивают общий
лимит между процессами и после перезапуска. При недоступной БД защищённое
действие не выполняется. В ключах хранится SHA-256 от действия, окна и
идентификатора. Счётчик перестаёт расти после первого превышения лимита.

Это окна, отсчитываемые с первого запроса: по окончании окна квота
восстанавливается. Длинное часовое окно дополнительно сдерживает частые
короткие серии. IP может быть общим для нескольких покупателей за одним
роутером; пороги следует подбирать по фактической работе магазина.

Раз в минуту каждый процесс удаляет до 1000 давно просроченных счётчиков и до
1000 Telegram-сессий, истёкших больше суток назад. Индексы по `expiresAt`
и блокировка строк с `SKIP LOCKED` ограничивают работу очистки.

## IP и Render

При `RENDER=true` используется валидный `CF-Connecting-IP`, переданный
защищённым входом Render/Cloudflare. На локальном сервере используются данные
сокета, а произвольные `X-Forwarded-For` и `CF-Connecting-IP` игнорируются.
Если на Render заголовок отсутствует или неверен, используется адрес сокета:
это может объединить покупателей в общую квоту. При изменении схемы хостинга
нужно проверить способ получения IP и адаптировать `client-identity.ts`.
Нельзя устанавливать `RENDER=true` на сервере, доступном в обход доверенного
прокси: тогда клиент сможет подставлять заголовок сам.

IPv4 и его IPv6-mapped представление дают один ключ. IPv6 группируется по
подсети `/64`, чтобы смена адреса внутри подсети не давала новую квоту.

Описание инфраструктуры: [Render](https://render.com/articles/how-render-handles-ddos-attacks),
[заголовки Cloudflare](https://developers.cloudflare.com/fundamentals/reference/http-headers/#cf-connecting-ip).
Эти ограничения защищают операции приложения; большой поток запросов до БД
должна сдерживать также защита на входе хостинга.

## Telegram-коды

Пять неверных шестизначных кодов блокируют сессию. Счётчик в БД нельзя сбросить
повторным открытием бота. Ответ: `429` с кодом `TELEGRAM_SESSION_LOCKED`.
Нужна новая сессия через кнопку начала входа; ожидание не разблокирует старую.

Верный код атомарно помечает сессию использованной. Параллельные запросы не
могут получить несколько токенов по одному коду. Повторный `/start` возвращает
прежний код без продления срока действия. Сессия может быть привязана только
к одному Telegram-аккаунту, а код отправляется только в личный чат.

## Публикация и проверка

Перед запуском нового backend применить миграции к нужной БД:

```powershell
cd sushi-backend
npx.cmd prisma migrate deploy
npm.cmd run build
```

Миграция `20261027120000_limit_sensitive_requests` добавляет счётчики и поле
`failedAttempts`. Старые сессии получают ноль неудачных попыток.
Затем развернуть backend. Старые клиенты тоже получают серверную защиту;
обновлённые веб и приложение показывают пояснения при `429`.

`npm test` проверяет SQL на изолированном движке PostgreSQL PGlite, без
обращения к Neon или реальным аккаунтам Telegram. Проверяются параллельные
запросы, общая квота, восстановление окна, очистка, привязка аккаунта,
блокировка после пяти ошибок и одноразовое использование кода.
